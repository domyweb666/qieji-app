# 手感診斷：為什麼不順、怎麼改的（2026-11-04）

> 多米真機回報四點，加一句「我的唯一標準就是極致的手感」。這份回答「到底該怎麼優化、該怎麼改」。
> 真機數字來自 11/04 早上那次測試（開發版，`[perf]` 印在跑 tunnel 的終端機）。

## 結論

三個問題都不是調數字能解決的，是做法本身卡住了：

1. **切換有延遲**：主因不是慢，是我們自己在等。點下去先等面板收完（約半秒）才開始換紙。
2. **拖完會閃**：行的位置被兩套東西分開管（版面排一次、動畫位移一次），放手那一刻兩邊換手，落在不同格就閃。之前修過好幾輪，都是在調先後，只要是兩套就不可能根治。
3. **一千行卡**：全部的行都掛在畫面上，每一行又是完整的一套（輸入框、四個手勢、六份動畫）。之前「只做看得到的行」「分批掛」都是在這個底上補。

所以這次改做法，不再補：**結果當下發生；位置只有一套；只掛畫面附近的行；每行只放畫得出來的東西。** 這四句也寫進了 `.vibe/規矩檔.md` 的「手感是最高標準」。

## 真機量到的（改之前）

| 操作 | 數字 |
|---|---|
| 掛上 2～4 行的紙 | 107～140 毫秒（JS 忙的時候到 237） |
| 掛上 22 行的紙 | 293～327 毫秒，JS 同時卡住 250～340 毫秒 |
| 掛上 1000 行的紙 | 496 毫秒 |
| 1000 行捲動中 | JS 一直卡，每段 120～950 毫秒；畫面最差一秒只畫 14 格，最長一格 196 毫秒 |

從這些數字推得出：一行完整的行大約 9 毫秒（開發版），一張空紙本身也要 100 毫秒以上。

## 每個問題的時間線

### 1. 切換清單（點下去到看到新紙）

| 階段 | 改之前 | 改之後 |
|---|---|---|
| 等面板收完 | 約 510 毫秒（彈簧感知 340，實際約 1.5 倍） | **0**（下一格畫面就開始換，面板同時讓開） |
| 掛上新紙 | 110～330 毫秒 | 2～4 行的紙會少一點；22 行的紙應該少很多（要真機量） |
| 新紙淡入 | 150 毫秒，從奶油底淡入（會閃） | 150 毫秒，從上一張的顏色融過去 |
| 多跑的事 | 舊紙卸載時多重畫一次、整份存檔、推小工具 | 有改才重畫；存檔、小工具排到後面 |

改之前從點下去到看到新紙要 0.8～1 秒，其中一半以上是白等的。

### 2. 排順序放手

| | 改之前 | 改之後 |
|---|---|---|
| 行的位置 | 版面排好＋位移 | 全部是 UI 執行緒的位置表＋位移，版面不管 |
| 放手 | JS 改資料 → React 重排版面（一格）→ 位移歸零（另一格），兩格錯開就閃 | UI 執行緒同一格把位置表換好、位移歸零；React 之後才知道，畫面不會動 |

### 3. 一千行

| | 改之前 | 改之後 |
|---|---|---|
| 掛著幾行 | 1000 行（約 9000 個原生元件） | 畫面前後各多 1.25 個螢幕，約 30～46 行 |
| 一行有什麼 | 輸入框＋鏡像文字＋4 個手勢＋6 份動畫 | 字＋六個點＋1 份動畫 |
| 手勢 | 每行各一組 | 整張清單一組，手指碰到時查位置表 |
| 輸入框 | 看得到的每行都有 | 只有正在打的那一行 |
| 捲動中 | 每捲 1/4 螢幕換一批輸入框和手勢，上千個同層元件都要比對 | 只多掛、拆幾行字 |

## 已經驗到哪裡

**網頁預覽走過（只驗邏輯，驗不了手感）：** 點一行打字、換點別行（只有一個輸入框、字沒丟）、往右滑劃掉、往左滑刪除、長按選單刪除（淡出、下面滑上來）、復原、按 ＋ 記一行（其他行滑下去）、打字換行（下面的行滑下去）、拖六個點（逐格記錄，放手前後每一行位置連續）、千行紙中段拖（順序對）、切換清單（點下去約 80 毫秒紙就換了）、新的一張（輸入框約 70 毫秒升起）、改磚上的字（兩個字按好留在當頁、紅字紅框、字還在；改一個字才存）。千行紙快速捲 300 格：沒有一格空白，最多掛 46 行。測試 150 條、tsc、lint、裸數字檢查都過。

**還沒驗、只有真機驗得到：**

- 手感本身，全部
- 點一行時字會不會跳：一般文字跟輸入框差 2.86 點是讀 React Native 原始碼算的，中文字型可能還差一點點，要看真機
- 換點別行時鍵盤會不會收了再開：現在每次換行都新掛一個輸入框，舊的等焦點移走才拆
- 行首刪除鍵併行時鍵盤會不會閃一下：那一行是直接拿掉的
- 排順序、滑動的手勢設定在 iOS 跟網頁不一定一樣（規矩檔有前例）

## 第一次真機之後（同日）

- **數字變好了（開發版）：** 打開千行紙 496 → 129 毫秒；掉格多半每秒 1～2 格、最長一格 26～44 毫秒（資料還少，操作也不完全一樣）
- **拖把手壞了：** 手勢接到手指、也查對行，但一啟動就被取消（`began` 之後馬上 `finalize`）。推斷：拿起那行 `zIndex` 變了，原生把排在它後面的兄弟拆下來重裝，把手的偵測元件也是兄弟，一拆手勢就斷；網頁的 zIndex 是 CSS 所以測不出來。修法：行全部包進自己一層。**還沒真機驗**
- **捲到底刪一行整頁跳：** 內容變短那一刻系統把捲動位置一次拉回來（原因是推斷的）。改成捲動位置跟其他行同一個時鐘退回去，撐高的那塊等滑完才收。網頁逐格驗過，**還沒真機驗**

## 一個要更正的說法

我中途說過「每畫一行，JS 都要停下來向畫面執行緒同步問十幾個值」。查證之後不是每次：只有值在畫面執行緒變過才會同步問，影響比我講的小。新的寫法還是避開了（掛上那一刻不去要整張位置表），但這不是主因。

## 下一層（要重建，先不動）

1. **在正式版判斷手感**：開發版的 JS 和原生都比正式版慢好幾倍。不重建也能先看正式版的 JS：`npx expo start --tunnel --no-dev --minify`。原生那段要 `preview` 建置才看得到（花 EAS 額度，要先問多米）。
2. **動畫不走版面**：Reanimated 有一個開關 `IOS_SYNCHRONOUSLY_UPDATE_UI_PROPS`，位移、透明度直接改原生元件，不用每格重算整棵樹。這是實驗性的，而且要重建，等這輪真機結果出來、知道還卡在哪再決定。
