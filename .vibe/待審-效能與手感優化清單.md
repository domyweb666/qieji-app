# 待審：效能與手感優化清單

> 2026-10-31 多米問「還有什麼性能問題可以優化」「手感能不能提升（例如新增一行加震動）」「為什麼網頁版的編輯手感比 iOS 版好」。
> 這份只是診斷與建議，一行程式都沒改。每一項標了：影響多大、風險、要不要真機。多米勾選後才動工。
> 對照來源：`E:\茄記\easynote\index.html`（網頁版）與 `src/components/Paper.tsx`（iOS 版）。

## 一、網頁版的編輯手感為什麼比較好

先講結論：**兩邊的滑動、拖曳、門檻、動畫時長幾乎一字不差**（都是 14 起手、90／25% 劃掉、110／30% 刪除、150／180ms）。差的不是手勢，是**「從想到一句話，到那句話出現在紙上」中間要做幾個動作**。

| # | 網頁版 | iOS 版 | 影響 |
|---|---|---|---|
| 1 | **點一下**那行就能打字，游標落在**點的位置** | 要**點兩下**，而且游標跳到**行尾**；想改句子中間的字＝點兩下＋再點一下＝三下 | ★★★ 最大 |
| 2 | 打字中按 **Return ＝ 在這行下面長出新的一行**，游標接著打；在空行按 Return ＝ 收鍵盤 | Return ＝ 在同一格裡換行。要新的一行只能按 ＋，而且 ＋ 一定插在**最上面**、整頁捲回頂端 | ★★★ |
| 3 | 正在打的那行**底色變亮**，右邊出現 ✕ | 沒有任何「這行是現在這行」的視覺狀態，只有游標 | ★★ |
| 4 | 字 **20px**、行高 1.5 | 字 **17pt**、行高 27 | ★★（看起來寬鬆、字大好打） |
| 5 | 行首按 Backspace ＝ **併到上一行**（游標停在接點） | 只有整行是空的才會刪；有字的行不會併 | ★ |
| 6 | 貼多行文字 ＝ 自動拆成多行 | 留在同一格 | ★ |
| 7 | 點清單底下的空白 ＝ 開新的一行 | 空白區刻意不反應 | ★（這是多米決定的，列出來只是對照） |

**為什麼第 1、2 項是關鍵**：網頁版「紙上任何一行、任何位置，點了就打；打完 Return 就是下一行」，整個過程手不用離開鍵盤、眼不用離開那一行。iOS 版每次要下一行都得找 ＋、畫面跳到頂端、再把眼睛找回來。這就是「說不上來，但直覺上網頁比較順」的來源：**不是哪個動作慢，是動作變多了，而且每個動作之間視線要移動**。

### 建議（照順序）

**A1. Return ＝ 在這行下面開新的一行**（對應 #2）
- 做法：行的輸入框加 `submitBehavior="submit"`、`enterKeyHint="next"`，`onSubmitEditing` 時把游標後面的字切出去變成新的一行插在**下面**（不是最上面），游標落在新行開頭；空行按 Return 就收鍵盤。右下 ＋ 和膠囊 ＋ 不動，照舊插最上面。
- 代價：一格裡不能再用 Return 換行（貼上帶換行的文字仍然可以留在同一格；舊資料不動）。`Paper.tsx` 第一段註解寫的「換行留在同一格」會改掉，這不在 HANDOFF 的定案清單裡，但要多米點頭。
- 風險：中。鍵盤相關，**一定真機**。

**A2. 點一下就進編輯（先試，真機不過就退回點兩下）**（對應 #1）
- 當初改成點兩下是因為「一下會誤觸」。那時候輸入框自己收觸控；現在輸入框上面已經蓋了板子、點擊走的是手勢系統的 `useTapGesture`，手指一移動超過 10 點手勢就作廢，上下捲動理論上不會再觸發它。所以只要把 `numberOfTaps: 2` 改 1，可能就能一下進編輯、又不會捲動誤觸。
- 游標位置：手勢系統拿得到點在哪，但 React Native 沒有「座標 → 第幾個字」的 API，所以第一下仍落在行尾，想改中間的字要再點一下（兩下，比現在三下少一下，比網頁多一下）。
- 風險：中。這是推翻 2026-10-31 的定案，**只建議真機試一輪**，誤觸還在就立刻退回。

**A3. 正在編輯的行底色變亮**（對應 #3）
- `editing` 已經有了，加一個底色即可（要新增一個 token，例如 `rowEditingBg`，淺色深色各一組）。
- 風險：低，網頁預覽就看得到。

**A4. 字放大到 20、行高跟著調**（對應 #4）
- 改 `tokens.ts` 的 `bodyLine`，`rowMin` 可能要跟著動。對比檢查表不受影響（只是字級）。
- 風險：低，但會動到整張紙的密度，要多米看過。

**A5. 行首 Backspace 併到上一行**（對應 #5）
- 要用 `onSelectionChange` 記住游標位置才知道「在行首」。小改，但輸入法（注音組字中）可能干擾，**真機**。
- 風險：中低。

## 二、觸覺回饋：現況與缺口

現在只有三個事件有震動，而且三個都是同一種（`selectionAsync`，最輕的「嗒」）：劃掉、拖曳開始、長按開選單。網頁版 Safari 完全沒有震動 API，所以這一塊是 iOS 版**只贏不輸**的地方，值得補。

| 事件 | 現在 | 建議 | 為什麼 |
|---|---|---|---|
| ＋ 新增一行（右下 ＋、膠囊 ＋） | 沒有 | `impactAsync(Light)` | 多米提的。「生出一個東西」用輕碰撞，跟「選到」區分 |
| 右滑**越過**劃掉門檻 | 放手、動畫跑完才震（晚約 150ms） | 改成**手指越線那一刻**震一次（`selectionAsync`），放手不再震 | iOS 郵件、備忘錄都是越線震，這是「我知道你要幹嘛了」的回饋；現在的時機太晚，像事後通知 |
| 左滑越過刪除門檻 | 沒有 | 同上，越線震一次 | 刪除沒有任何觸覺，放手前不知道有沒有滑夠 |
| 拖曳排序**經過**另一行 | 沒有 | `dragTo` 每變一次 `selectionAsync` | 系統排序的「咔、咔」感；現在只有拿起來那一下 |
| 拖曳放下 | 沒有 | `impactAsync(Light)` | 落地感 |
| ⋯ 選單換顏色 | 沒有 | `selectionAsync` | 選單不關，震一下才知道有換到 |
| 釘選／取消釘選 | 沒有（只有 toast） | `impactAsync(Light)` | 可有可無 |
| 刪除這張、永久刪除、清空 | 沒有 | **不加** | 系統的刪除也不震；破壞性動作靠確認框，不靠震動 |
| 點兩下進編輯、∧ ∨ 切行、收鍵盤 | 沒有 | **不加** | 鍵盤出現本身就是回饋，再震會吵 |

- 做法：都走 `tokens.ts` 的 `HAPTIC` 表（一種事件一種觸覺），新增 `add`、`swipeArm`、`dragPass`、`dragDrop`、`color` 幾個名字；畫面程式只呼叫 `haptic('add')`。
- **越線震**要在滑動的 worklet 裡判斷：加一個 `armed` shared value，`onUpdate` 裡跨過門檻且 `armed` 還是 0 就設 1 並 `scheduleOnRN(hapticArm)`；退回門檻內就歸 0。`hapticArm` 必須是**模組層級**的函式（跟 `dismissKb` 一樣），不能是 tokens 裡的函式——規矩檔的坑。**一定真機**。
- 風險：新增一行、換色、拖曳經過＝低（JS 端）；越線震＝中（worklet）。

## 三、效能：真的值得動的、以及不要動的

先講整體：這個 app 目前的資料量（幾十張紙、每張幾十行）下，**沒有一個地方是「慢到看得出來」的**。網頁版手感好不是因為它比較快。底下是「以後資料多了會先痛」或「現在就能更順」的點。

### 值得動（照優先）

**P1. 拖曳排序走 JS 執行緒，手指快時會跟不上**
- `grip` 手勢是 `runOnJS: true`，每一格畫面都要跨到 JS 算 `dragTo`，再寫回 UI 執行緒。JS 忙的時候（例如同時在重畫）被拖的那行會慢半拍。
- 做法：`mids`（每行中點）放進 shared value，`move` 的計算搬進 worklet，只有 `end` 回 JS 改資料。
- 風險：中，worklet 改動**一定真機**。影響：拖曳更黏手指。

**P2. ＋ 新增一行、刪一行，會讓紙上每一行都重畫一次**
- `Line` 的 memo 比對了 `index` 和 `count`。新的一行插在最上面，每一行的 `index` 都 +1；刪一行，每一行的 `count` 都 −1。所以主要動作（＋）就是最貴的動作：每行重建 5 個手勢、5 個動畫樣式。幾十行大概十到三十毫秒，剛好疊在鍵盤升起那一刻。
- 做法：`count` 只用在 VoiceOver 的「往下移」能不能顯示，改傳 `isLast` 布林；`index` 給拖曳位移和「往上移」用，可以改成 `isFirst` 布林＋把拖曳用的 index 放 shared value。
- 風險：中（碰到拖曳位移的 worklet，**真機**）。影響：按 ＋ 那一下更乾。
- 建議：**先量再做**。開 React DevTools Profiler 在網頁預覽按 ＋ 看一次 commit 多久；低於 16ms 就不用動。

**P3. 啟動：讀完資料前是一片空白奶油色**
- `_layout.tsx` 在 `store.load()` 完成前畫一個空 View，啟動畫面先消失、閃一下空白、再出現紙。
- 做法：`expo-splash-screen` 的 `preventAutoHideAsync()`，`ready` 之後再 `hideAsync()`。這是感受上的「開得快」，不是真的快。
- 風險：低。Expo Go 上啟動畫面是 Expo Go 的，正式建置才看得到完整效果。

### 可以順手、但沒急迫

- **P4. 三張茄子 PNG 各 120～135 KB**（`face-flat*.png`，450×512）。舊的角色圖都是 WebP 約 19 KB。轉 WebP 可省約 350 KB 安裝包；畫面上看不出差別（顯示才 96pt）。
- **P5. `react-native-svg` 在 iOS 上白載**：`Sym.tsx` 靜態 import `Icon.tsx`（網頁預覽用的線條圖示），iOS 根本不會畫，但模組在啟動時照樣初始化。改成非 iOS 才 `require`。省幾毫秒啟動，低風險。
- **P6. 目錄搜尋每打一個字，每張紙都重組一次全文字串**（`visibleNotes`），而且色磚沒有 memo。幾十張紙無感，幾百張開始會頓。等真的有幾百張再說。

### 不建議動的（寫下來免得下次又討論）

- **每 0.25 秒把整份資料 JSON.stringify 一次**（打字中）：現在資料量下不到 1ms，不用改成局部存檔。
- **一行要畫兩次字（隱形文字撐高度＋輸入框）**：Fabric 的多行輸入框理論上會自己長高，但前面兩個 commit 就是在修這裡的邊界問題，拆掉要重測一輪，收益是每行省一個 Text，不值得。
- **全部的行都掛在 ScrollView 裡、沒有虛擬化**：一張紙超過一兩百行才會有感，而且虛擬化會打壞「對焦→捲到那行」和鍵盤邏輯。等真的有人一張紙寫兩百行再說。
- **換成 MMKV 這類更快的儲存**：Expo Go 用不了，而且 AsyncStorage 在這個資料量下讀寫都在毫秒級。

## 四、用 iOS 原生功能把紙露在顯眼處（桌面小工具、鎖定畫面等）

多米 2026-10-31 問「能否使用 iOS 的原生功能，顯示在顯眼處」。這裡把「顯眼處」理解成 app 外面的位置：桌面、鎖定畫面、控制中心、Siri。

### 先講前提：Expo Go 做不到，要「開發版建置」

- 這些全部都是 app 的「延伸」（extension），要多一個原生 target。Expo 官方 `expo-widgets` 文件寫明「This library is not available in the Expo Go app」。
- 沒有 Mac 也能做：`eas build --platform ios` 在 Expo 的雲端 Mac 上編譯簽章，裝到 iPhone 走 **TestFlight**（要 Apple Developer Program，一年 99 美金）或內部發佈（要先登錄裝置 UDID）。
- 本機建置（`--local`）要 Xcode，沒 Mac 不行。
- 換句話說：**這一步＝從「Expo Go 測」換成「自己的 app 測」**。HANDOFF 已經提過圖示要正式建置才看得到，是同一道門。跨過去之後，圖示、啟動畫面、小工具一起到位。

### 能放在哪裡、各自適合茄記什麼

| 位置 | 系統版本 | 適合放什麼 | 做法 | 風險／成本 |
|---|---|---|---|---|
| **桌面小工具**（小／中／大） | iOS 14+；可互動 17+ | 上次開的那張紙：清單名＋前幾行；點了直接開那張。中型可以放一顆「＋ 記一行」按鈕（可互動小工具） | `expo-widgets`（官方，SDK 58 有，用 Expo UI 元件寫，不用寫 Swift） | 中。小工具是獨立執行環境，不能用 React hooks、不能讀 app 狀態；app 要用 `updateSnapshot` 把紙的資料推過去，資料透過 App Group 共用 |
| **鎖定畫面小工具** | iOS 16+ | 一行字：紙名＋剩幾行沒劃掉；或一顆 ＋ 捷徑 | 同上，`supportedFamilies` 加 `accessoryRectangular` / `accessoryInline` | 跟桌面小工具同一包 |
| **控制中心按鈕** | iOS 18+ | 一顆「開茄記記一行」（連鎖定畫面底下兩顆也能換成它） | `@bacons/apple-targets`（社群，要寫一點 Swift），`expo-widgets` 目前沒有 | 中高，要碰 Swift |
| **Siri／捷徑（App Intents）** | iOS 16+ | 「嘿 Siri，茄記記一下 XXX」不用開 app 就寫進紙上 | `@bacons/apple-targets` App Intents target | 中高，要寫 Swift，而且要跟 AsyncStorage 的資料互通（小工具／Intent 讀不到 AsyncStorage，要改成 App Group 共用的檔案） |
| **分享延伸**（從別的 app 把字分享進茄記） | iOS 8+ | Safari 選字 → 分享 → 茄記 → 變成一行 | `@bacons/apple-targets` share target | 中高 |
| **即時動態／動態島** | iOS 16.1+ | 不適合。這是給「進行中」的事（外送、計時），紙不是進行中的事 | — | 不建議 |
| **長按圖示的快速動作** | iOS 13+ | 「新的一張」「記一行」 | `expo-quick-actions`，一樣要開發版建置 | 低，最便宜的一個 |

### 最大的技術坎：資料共用

現在資料存在 AsyncStorage（`colornotes.v1`）。小工具、Siri、分享延伸都是**另一個行程**，讀不到它。要做任何一個，都得多一步：app 每次存檔時，把「要露出去的那部分」（例如上次那張紙的名字和前十行）另外寫進 App Group 的共用區，小工具只讀那份。反過來（小工具的 ＋、Siri 寫進來）則是延伸端寫一個「待處理」檔，app 下次打開再合併進 AsyncStorage。這不難，但要設計清楚誰是真相來源，不然會出現「Siri 記的那行不見了」。鐵則「key 永遠是 colornotes.v1、欄位只能加」不受影響。

### 建議

1. **先決定要不要跨「開發版建置」這道門**。這是前提，而且會同時解掉圖示、啟動畫面兩件事。要跨的話，第一步是申請 Apple Developer Program 和設定 EAS，跟小工具無關。
2. 跨了之後，第一個做**桌面小工具（中型）＋鎖定畫面一行**，只讀不寫：顯示上次那張紙的名字和前幾行，點了開 app。用官方 `expo-widgets`，不碰 Swift。這一包最便宜、最顯眼。
3. 「不開 app 就記一行」（可互動小工具的 ＋、Siri）放第二輪，因為要先把資料共用設計好。
4. 控制中心、分享延伸看用不用得到再說。

參考：[Expo 官方 expo-widgets 文件（SDK 58）](https://docs.expo.dev/versions/v58.0.0/sdk/widgets/)、[用 Expo 做小工具、控制中心、即時動態的實作記錄（@bacons/apple-targets）](https://dev.to/oddeggs/widgets-controls-and-live-activities-from-an-expo-app-2i28)、[不用 Mac 發 iOS app 的流程（EAS Build）](https://vp0.com/blogs/do-i-need-mac-publish-ios-app)。

1. ~~**A1（Return 開新行）＋ A3（編輯中的行變亮）＋ 震動表的「新增一行」「換色」「拖曳經過」**~~ **已做（2026-10-31，多米選「做第一輪」）**，網頁預覽過（Return 切行、編輯中變亮），**震動與鍵盤行為待真機**。做法：行的輸入框 `submitBehavior="submit"`＋`enterKeyHint="next"`，`onSubmitEditing` 把游標後面的字切到正下方的新行；不受控輸入框被程式改字時用 `rev` 重掛。新 token：`rowEditingFill`、`haptic('add'|'color'|'dragPass')`。
2. ~~**A2（點一下進編輯）**~~ **已改（2026-10-31，多米選「試點一下編輯」）**：`numberOfTaps` 2 → 1，提示字改「點一下改字」，其他一行沒動。**待真機**：上下捲動時碰到字會不會跳鍵盤、捲動中用手指停住畫面會不會進編輯、長按和右滑有沒有被搶。誤觸就把 `numberOfTaps` 改回 2、提示字改回。游標仍落在行尾（RN 沒有座標轉字位的 API），要改中間的字再點一下。
3. ~~**越線震（滑動 worklet）＋ P1（拖曳搬進 worklet）**~~ **已做（2026-10-31 第三輪，多米選「越線震＋拖曳 worklet」）**。滑動：`armed` shared value 記手指在哪一區，換區那一刻 `scheduleOnRN(hapticArm)`，放手不震（長按選單、VoiceOver 的劃掉仍在放手震）。拖曳：`dragMids` 放 shared value，把手的 `onUpdate` 在 UI 執行緒算 `dragTo`，拿起、放下才回 JS；拿起那幾毫秒 `dragIdx` 還是 -1 先不算。網頁預覽：滑動劃掉正常、慢拖把手順序會變。**待真機**：越線震的時機對不對、退回再越過會不會重複震到煩、拖曳有沒有更跟手、worklet 有沒有崩潰。
